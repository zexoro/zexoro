## 1. Components

| Component | Where | Notes |
| --- | --- | --- |
| NSIS toolset | `zexoro/nsis-toolset` | NSIS 3.13 built from source. `makensis` built natively per host (linux-x64, linux-arm64, macOS universal, win-x64); stubs and plugins cross-compiled once with mingw-w64 on Linux. Published as GitHub releases tagged `v3.13-zexoro.<n>`: `nsis-3.13-<rid>.tar.gz` (`<rid>` = `linux-x64`, `linux-arm64`, `osx`, `win-x64`) plus `SHA256SUMS`. |

| TOML parser | `Zexoro.Toml` | TOML 1.1.0 into a document model that keeps line and column for every key and value. Conformance: the `toml-test` 2.2.0 valid and invalid cases, vendored under `tests/`. |
| Configuration | `Zexoro.Core` | Typed model of `zexoro.toml` with validation. Unknown keys are errors, so typos never pass silently. Every error points at a line and column. |
| Authenticode | `Zexoro.Signing` | Signs PE files (exe, dll) from a PFX with RSA or ECDSA keys, with an RFC 3161 timestamp. CMS `SignedData` is built with `System.Formats.Asn1`: `System.Security.Cryptography.Pkcs` is not part of the shared framework, and the runtime-dependency rule keeps it out. |
| NSIS back end | `Zexoro.Formats.Nsis` | Generates an `.nsi` script from the configuration, runs the bundled `makensis`, signs the results. |
| CLI | `Zexoro.Cli` | `init`, `pack`, `doctor`. |

## 2. Shipping the toolset

The CLI stays a single file. At build time, the release workflow downloads the pinned toolset for the target RID (version and SHA-256 recorded in `eng/toolsets.json`) and embeds it as a resource. At run time, zexoro extracts it once into a versioned cache directory (`%LOCALAPPDATA%\zexoro`, `~/Library/Caches/zexoro`, `$XDG_CACHE_HOME/zexoro`) and verifies the hash before each use. Nothing is downloaded at run time.

Implementation (step 4):

- `eng/toolsets.json` pins, per toolset, a version and per RID an archive URL and SHA-256. `eng/Toolsets.targets` (imported by `Zexoro.Cli`) embeds the archive for `$(RuntimeIdentifier)` when one is set (publishing; a RID without an entry is a build error) and otherwise the host RID's (plain build and test; a host without an entry builds without a toolset). Downloads go to `~/.nuget/zexoro-toolsets/<name>/<sha256>/` (`ZEXORO_TOOLSET_CACHE` overrides) and are verified on every build, so builds are offline once the archive is cached. The resource is `Zexoro.Toolsets.<name>.tar.gz`; version and hash travel as assembly metadata.
- Extraction (`ToolsetCache`, `System.Formats.Tar`): `<cache>/toolsets/<name>-<version>-<hash prefix>/`, without `Docs/` and `Examples/`. The archive hash is checked before extracting; a manifest with the SHA-256 (and Unix mode) of every file is written last, and every use re-hashes the files against it. A missing or modified file triggers a fresh extraction. Extraction goes to a temporary sibling and is renamed into place, so concurrent runs either win the rename or use the winner's directory. Only regular files and directories are accepted; absolute and `..` paths are rejected.
- `ZEXORO_NSIS_DIR` points at an NSIS directory to use instead (development). `ZEXORO_CACHE_DIR` overrides the cache root.
- `makensis` runs from `Bin/` (it derives NSISDIR from its own location), with `-WX -NOCONFIG`, and on Linux and macOS with `LC_ALL=C.UTF-8`: under the C locale it aborts while generating language tables.

## 3. Installer behavior

- **Layout** (update contract): `<root>\app\…`, `<root>\zexoro-install.json`, `<root>\uninstall.exe`.
- **Roots:** per-user `%LOCALAPPDATA%\Programs\<name>` (no elevation); per-machine `%ProgramFiles%\<name>` (64-bit view for x64 and arm64 apps, elevation requested by the installer).
- **Identity:** uninstall key `HKCU|HKLM\Software\Microsoft\Windows\CurrentVersion\Uninstall\<app.id>` with name, version, publisher, icon, install location, estimated size, `UninstallString`, `QuietUninstallString`, `NoModify`, `NoRepair`.
- **Upgrade:** if the key exists, the installer refuses to run while the application is running, removes `<root>\app` and installs the new files, then updates the key. Same version reinstalls; a lower version is refused (exit code 3 in silent mode).
- **Uninstall:** removes the root, shortcuts and key. User data is kept; `[windows.uninstall] remove = [...]` lists extra paths to delete.
- **Shortcuts:** Start menu by default; desktop optional. Both point into `<root>\app\`.
- **UI:** Modern UI 2, English only: optional license page, progress, finish page with a "launch" option. Silent mode `/S` and `/D=` work for every scope.
- **Installer metadata:** version resource from the SemVer core (`1.2.3` → `1.2.3.0`), the application icon, Unicode, LZMA solid compression. The stub is x86-unicode, which runs on x64 and arm64 Windows.

Implementation (step 4):

- **Architecture** comes from the main executable's PE header (x86, x64, arm64). x64 installers refuse to run on 32-bit Windows, arm64 installers anywhere but arm64 Windows. Per-machine x86 apps go to `%ProgramFiles(x86)%` and the 32-bit registry view.
- **Output name:** `<name>-<version>-win-<arch>.exe` in `dist/` next to the configuration (`--output` overrides), where `<name>` is `app.name` reduced to letters, digits, `.`, `-` and `_` (for example `ExampleNotes-1.2.3-win-x64.exe`). No "setup" suffix: Windows applies installer compatibility shims to such names, and makensis warns about them.
- **Install record** `zexoro-install.json` is generated at pack time (schema, app, version, os, arch, format, scope, `strategy` = `replace` per-user or `reinstall` per-machine) and installed as a file. `channel`, `feed` and `keys` are added when updates become configurable.
- **No directory page.** An existing install is always upgraded where it is (its `InstallLocation` wins over the default and over `/D=`); `/D=` chooses the location of a fresh install.
- **Version comparison:** the key also holds `ZexoroVersionOrder`, a string whose ordinal order is SemVer precedence (`NsisVersionOrder`); the installer compares it with `CompareStringOrdinal`. Whatever changes the installed version (the updater for `replace`) must update it. Major, minor and patch must each be at most 65535 (version resource limit), checked by `pack`.
- **Running application:** the installer and uninstaller try to open the main executable for writing (impossible while it runs) and offer Retry/Cancel. The upgrade then renames `<root>\app` to `app.old` (which fails if files are in use) and deletes it before installing.
- **Exit codes:** 0 success, 1 cancelled, 2 aborted (unsupported Windows, or a per-machine install without administrator rights), 3 a newer version is installed, 4 the application is running or its files are in use.
- **Uninstall** deletes only what the installer and updater create (`app`, `app.old`, `app.new`, `zexoro-install.json`, `zexoro-updater.exe`, `uninstall.exe`), then the root only if it is empty, so a `/D=` that pointed at an existing folder does not lose that folder's other files. `remove` entries map `%LOCALAPPDATA%` and `%APPDATA%` to the current user (for a per-machine install: the user who runs the uninstaller) and `%PROGRAMDATA%` to the all-users application data folder.
- **Launch** from the finish page runs the application as the user: per-machine installers start it through Explorer, so it does not inherit elevation.

## 4. Signing order

1. Application PE files that are not already signed (main executable by default; `sign = "all"` covers every PE file).
2. The uninstaller, through NSIS `!uninstfinalize`, which calls the running zexoro executable's internal `sign-file` command.
3. The installer, through `!finalize`.

Without a certificate, signing is skipped and `pack` prints a notice.

Application files are signed in the staging copy, never in the input directory. For steps 2 and 3, `pack` writes the certificate path and timestamp URL to a request file in the private staging directory plus a small wrapper script (`sign.sh`, or `sign.cmd` on Windows) that runs `zexoro sign-file --request <file> <target>`; the NSIS script calls only the wrapper, so no path ever needs NSIS quoting. The password reaches `sign-file` through the `ZEXORO_SIGN_FILE_PASSWORD` environment variable of makensis, never a file or a command line.

## 5. Tests

- **Unit**, on all three CI platforms: TOML conformance, configuration validation, script generation (snapshot), PE parsing and Authenticode hash, CMS structure, platform names.
- **Signature verification:** `osslsigncode verify` on Linux CI as an independent check (test-only tool).
- **End-to-end**, GitHub Actions:
  1. Pack two versions of a fixture app (framework-dependent `win-x64` publish, which cross-compiles from any OS) on Ubuntu, macOS and Windows, for both scopes, signed with a throwaway self-signed certificate. Version 1 contains a file that version 2 removes.
  2. On a Windows runner, for each scope: silent install v1 → check files, key, shortcuts, signature (certificate temporarily trusted) and that the app runs → install v2 over it → check the stale file is gone, there is one key with the new version → try installing v1 again and expect refusal → uninstall → check nothing is left except user data.
  3. The scripts live in `tests/e2e/windows/` (plain PowerShell) so they can also run over SSH on a real Windows machine.

## 6. Order of work

Each step is a branch merged into `dev` after CI passes.

1. `nsis-toolset`: build pipeline and first release.
2. Platform model and TOML parser.
3. Configuration model, `init`, `doctor`.
4. NSIS back end, toolset embedding, unsigned `pack`.
5. End-to-end Windows tests.
6. Authenticode signing, including the end-to-end signature checks.
7. Release workflow for the CLI (the same five RIDs as the toolset), README usage, example workflow for users. Then the `dev → main` pull request for review.
